來源：wiki/overview.md

痛點：AI 每次都從頭找

  • 上傳一堆檔案，查詢時才撈相關片段、現場拼答案
  • LLM 每次都「從頭重新發現知識」，沒有累積
  • 需要綜合五份文件的問題：每次都要重新找、重新拼
  • NotebookLM、ChatGPT 檔案上傳都屬於這類（RAG）
關鍵句：沒有東西被累積。
來源：wiki/concept-compilation.md、wiki/comparison-vs-rag.md

核心觀念：編譯一次，持續維護

  • 新資料進來：立刻讀完、萃取、編入現有 wiki
  • 交叉引用已建好、矛盾已標注、綜合已反映讀過的一切
  • wiki 是持久、複利（compounding）的資產
分工：人選來源、問好問題；LLM 做摘要、歸檔、記帳。
來源：wiki/concept-compilation.md

三層架構

raw/　原始來源不可修改，是 source of truth；Agent 只讀不寫
wiki/　知識頁LLM 全權生成與維護：建頁、更新、維護交叉引用
schema　AGENTS.md規範結構、慣例與 ingest/query/lint 工作流；人與 Agent 共同演化
整個 wiki 就是一個 git repo——版本歷史是現成的。
來源：wiki/concept-three-layers.md

三個操作

Ingest　編入新來源讀完、萃取、編入相關頁面
Query　查詢先讀 index 找頁面，答案帶出處
Lint　健檢定期檢查矛盾、孤兒頁、斷連結
來源：wiki/concept-operations.md

Ingest：一篇資料進來會發生什麼

讀來源→與你討論重點→寫摘要頁→更新相關頁→更新 index、記 log
  • 一份來源可能碰 10–15 個 wiki 頁
  • Karpathy 偏好一次一篇、邊做邊檢查
來源：wiki/concept-operations.md、wiki/source-01-karpathy.md

Query：回答要帶出處

  • 先讀 index.md 找相關頁，再深入內容
  • 好答案回寫進 wiki，不要消失在聊天紀錄裡
  • MindBase：記錄「讀了哪幾頁 vs 引用了哪幾頁」——該用而沒用的頁，事後 grep 得到
來源：wiki/concept-operations.md、wiki/concept-index-log.md、wiki/entity-mindbase.md

Lint：幫 wiki 健康檢查

  • 程式檢查：斷連結、斷引用、近重複頁——不經模型判斷，沒有誤報
  • 語意檢查：矛盾、過時主張、缺少的頁面
社群口訣：Extend, don't create——擴充既有頁，不要再建一頁。
來源：wiki/concept-operations.md、wiki/entity-mindbase.md、wiki/synthesis-failures.md

index.md 與 log.md

  • index.md：每頁一句話摘要，每次 ingest 就更新；查詢的入口
  • log.md：append-only；固定前綴「## [日期] 操作 | 標題」就能用 grep 解析
百頁規模：光靠 index 就夠，不需要向量資料庫。
來源：wiki/concept-index-log.md

LLM Wiki vs RAG

面向傳統 RAGLLM Wiki
整理時機查詢時現場拼ingest 時就整理
累積性沒有持久、複利
交叉引用無已建好
矛盾片段都撈得到維護時已標注
基礎建設embedding、向量索引index.md 就夠
成本每次查詢重付維護一次性
來源：wiki/comparison-vs-rag.md

來源：wiki/entity-student-llm-wiki.md、wiki/entity-mindbase.md、wiki/entity-crow.md、wiki/entity-liangdabiao.md

總結

  • 近重複頁 → Extend, don't create
  • 斷連結、斷引用 → 交給程式 lint
  • 資料矛盾 → 並列標注，不靜默覆蓋
一句話帶走：知識要編譯一次、持續維護，而不是每次重新推導。
